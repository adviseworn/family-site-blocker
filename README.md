# Family Site Blocker

A browser extension for Chrome, Edge, Brave and Firefox that blocks websites on a list. Its built-in list is `exampleadultsite.com` (the test case), 20 large adult sites, some newer ones the community list doesn't have yet (AI "companion", image and undress sites, and a few hookup and image sites), and a community list of some 64,000 more (StevenBlack/hosts's adult list, MIT), and you can add your own. From version 1.5.0 it also judges the pictures on every page and hides those that show nudity or, by default, anything suggestive, and from 1.6.0 the videos too, by their frames as they play (see **Pictures**). Each attempt to open a listed site is noted, with the time: the latest few on its settings page, the whole record on a page of its own (see **Blocked attempts**).

**Test case:** navigate to `exampleadultsite.com`. **Expected:** the website is blocked. With the extension loaded, you land on a "This site is blocked" page and nothing is fetched from the site. Under the Firefox lock, Firefox blocks it itself before the extension does, so you land on Firefox's own **Blocked Page** instead.

## Try it

You need Chrome, Edge, Brave or Firefox on a computer. Phones, tablets, Safari and browsers built into other apps can't load this extension.

First, get the files onto your computer. On this repository's GitHub page, click **Code**, then **Download ZIP**, and unzip the download. If someone sent you `family-site-blocker.zip`, unzip that instead.

### Chrome, Edge or Brave

1. Open the extensions page. Click the address bar at the top of the browser window, type `chrome://extensions` and press Enter (in Edge, `edge://extensions`). Or open the browser menu (**⋮** in Chrome, **⋯** in Edge), choose **Extensions**, then **Manage Extensions** if a submenu opens. Type the address rather than clicking it as a link: browsers don't let links open this page.
2. Turn on the **Developer mode** switch (top right in Chrome). A **Load unpacked** button appears.
3. Click **Load unpacked** and choose the `extension` folder inside the unzipped folder. The extension's settings page opens.
4. In a normal (not Incognito) window, type `exampleadultsite.com` in the address bar and press Enter. You should see "This site is blocked".
5. Click **Details** under Family Site Blocker and turn on **Allow in Incognito**. Browsers switch extensions off in private windows unless you do this, and the settings page tells you when it is still off.

If `chrome://extensions` comes up blank, you're probably not in Chrome, Edge or Brave. Firefox has its own steps below.

### Firefox

Firefox only keeps add-ons that Mozilla has signed. You can try this one straight away, but it stays loaded only until Firefox quits. To keep it after a restart, have Mozilla sign it first (see "Keep it installed" below).

**Try it (until Firefox quits)**

1. Click the address bar, type `about:debugging#/runtime/this-firefox` and press Enter. Or open the menu (**☰**), choose **Extensions and Themes**, click the gear (**⚙**) and choose **Debug Add-ons**.
2. Click **Load Temporary Add-on…** and choose the `manifest.json` file inside the `extension` folder of the unzipped folder. The extension's settings page opens.
3. If the settings page's **Is it working?** board has a line saying Firefox hasn't given the add-on access to websites, click **Allow access** and confirm. Without that access, sites on the list still open.
4. In a normal (not private) window, type `exampleadultsite.com` in the address bar and press Enter. You should see "This site is blocked". If Firefox is set to never remember history, every window is private, so do step 5 first.
5. For private windows, type `about:addons` in the address bar, choose Family Site Blocker and set **Run in Private Windows** to **Allow**. Firefox leaves this off for new add-ons, and the settings page tells you when it is still off.

When Firefox quits, it removes the add-on and the sites you added on the settings page.

**Keep it installed after Firefox quits**

Signing is free, and the add-on can stay unlisted, so it isn't published on Mozilla's site. GitHub can do steps 1 to 6 for you, or you can do them by hand.

To let GitHub do it, first save an API key from Mozilla in this repository, once. Signed in at [addons.mozilla.org/developers/addon/api/key](https://addons.mozilla.org/developers/addon/api/key/), generate credentials. Then on GitHub, open **Settings → Secrets and variables → Actions** and add two repository secrets: `AMO_JWT_ISSUER` with the "JWT issuer", and `AMO_JWT_SECRET` with the "JWT secret". For each version, open the **Actions** tab, choose **Sign with Mozilla** and click **Run workflow**. It uploads the add-on, waits for Mozilla to sign it, checks that the signed file holds exactly what was uploaded, and publishes a release named after the version with the signed `.xpi` and the Mac zip from step 6, then adds the Mac files to it from a GitHub-hosted Mac: the lock's profile and the installer package that closes Firefox's Option key (**Mac files for a release**, which can also be run by hand for a release that lacks them). If Mozilla already has that version, for example because you uploaded it by hand, it downloads the signed file instead. Download them from the repository's **Releases** page and carry on from step 7.

By hand:

1. Get the upload file: run `npm run package:firefox`, which writes `dist/family-site-blocker-firefox.zip`, or use the `family-site-blocker-firefox.zip` you were sent. Don't compress the `extension` folder yourself. Mozilla needs `manifest.json` at the top of the zip, and Finder's **Compress** puts it inside a folder. The zip's copy of `manifest.json` also leaves out the `service_worker` line, which only Chrome, Edge and Brave use.
2. Sign in at [addons.mozilla.org/developers](https://addons.mozilla.org/developers/) with a Mozilla account and choose **Submit a New Add-on**.
3. When asked how to distribute it, choose **On your own**, then upload the zip. Mozilla runs the same check as `.github/workflows/firefox-package.yml`, which finds no errors or warnings in this zip.
4. When asked whether you need to submit source code, choose **No**: the add-on's code isn't minified or compiled.
5. Submit the version. Mozilla signs it automatically. When it's ready, download the signed `.xpi` file from the version's page. Mozilla names it with a code plus the version number, like `a138dee9ad3f4f03aa63-1.1.1.xpi`, and Finder shows it with a blank document icon.
6. On a Mac, give it a clear name and the add-on's gate icon. Run `npm run package:signed --` followed by the path to the `.xpi`, for example `npm run package:signed -- ~/Downloads/a138dee9ad3f4f03aa63-1.1.1.xpi` (dragging the file into Terminal types its path). It checks that the file is Family Site Blocker, signed by Mozilla, and writes `dist/family-site-blocker-1.1.1.zip`. Double-click that zip in Finder to get `family-site-blocker-1.1.1.xpi` with the gate icon. It's the same signed file, so it installs the same way. To give it to another Mac, send the zip: the `.xpi` on its own arrives without the icon.

   Without Node, you can do this by hand. Rename the file, then open `extension/icons/icon128.png` in Preview and choose **Edit → Select All**, then **Edit → Copy**. Select the `.xpi`, choose **File → Get Info**, click the small icon at the top of the window and choose **Edit → Paste**. Neither the name nor the icon affects Mozilla's signature, and Firefox shows the add-on as Family Site Blocker either way.
7. In Firefox, remove the temporary copy if it's still loaded (on `about:debugging#/runtime/this-firefox`). Then open `about:addons`, click the gear (**⚙**), choose **Install Add-on From File…**, pick the `.xpi` and click **Add**. Tick **Allow this extension to run in Private Windows** if Firefox offers it.

   Double-clicking the `.xpi` in Finder won't work at first: macOS doesn't link `.xpi` files to Firefox, so it says no application is set to open it. To change that, select the file, choose **File → Get Info**, set **Open with** to Firefox and click **Change All…**. If Firefox isn't listed, choose **Other…**, set **Enable** to **All Applications** and pick Firefox. From then on, double-clicking a `.xpi` opens Firefox, which asks whether to add it.
8. Quit Firefox, open it again and visit `exampleadultsite.com`. It's still blocked, and sites you add on the settings page now stay too.

For a later version, raise `version` in `extension/manifest.json`, then run **Sign with Mozilla** again, or run `npm run package:firefox`, upload the new zip on the same add-on's page and carry on from step 5.

Version 1.3.0 asks for two permissions earlier versions didn't have, to note blocked attempts, 1.3.4 for a third, to add earlier visits from the browser's history, and 1.3.6 for a fourth, to remove bookmarks to listed sites (see **Blocked attempts**). Installing it by hand over an older version, Firefox asks you to accept them; under the lock, Firefox grants them itself. In Chrome, Edge and Brave, click the reload button under Family Site Blocker on the extensions page after replacing the folder's files, and if the extension shows as switched off with a note about new permissions, accept them there.

**Let it update itself (Firefox)**

From version 1.3.2, Firefox keeps the add-on up to date by itself, so a new version no longer has to be installed by hand in each account. The add-on names an update manifest, `updates.json`, which lists the signed versions and where to download them; Firefox reads it about once a day (and when someone chooses **Check for Updates** from the gear menu in the Add-ons Manager), and installs the newest version listed, after checking the file against the hash in the manifest. Firefox only fetches these without signing in, so they live on a public GitHub Pages site made from a second, public repository: `adviseworn/family-site-blocker-updates`, at `https://adviseworn.github.io/family-site-blocker-updates/`. Only the update manifest and the signed `.xpi` files go there (anyone can download those, the same files family members install; the source stays here). The newest version is there a second time as `family-site-blocker.xpi`, one name that never changes, which the Firefox lock installs from. **Sign with Mozilla** publishes them after each release through the **Publish updates** workflow, which rebuilds the site from every signed release (`scripts/updates-manifest.mjs`) and pushes it to that repository's `gh-pages` branch; GitHub Pages serves that branch, and switched itself on when the branch was first pushed. The repository exists and the site is up. For the workflow to push to it, once:

1. Make a key for it. In Terminal: `ssh-keygen -t ed25519 -N "" -C "family-site-blocker updates" -f ~/Desktop/updates-key`. That writes two files on the Desktop.
2. In the updates repository, open **Settings → Deploy keys → Add deploy key**, paste the contents of `updates-key.pub`, tick **Allow write access** and add it.
3. In this repository, open **Settings → Secrets and variables → Actions** and add a secret named `UPDATES_DEPLOY_KEY` with the contents of `updates-key` (the one without `.pub`, all of it). Then delete both files from the Desktop.
4. Open the **Actions** tab, choose **Publish updates** and click **Run workflow**, to see it work. It lists every signed release in `updates.json` and pushes the files; GitHub Pages shows a change a minute or two later. From then on **Sign with Mozilla** publishes each new version by itself; without the secret it still signs, and says in a warning that nothing was published.

If the updates repository ever has to be made again: a public repository named `family-site-blocker-updates` under the same account, empty; the first push of a `gh-pages` branch (step 4, or by hand) switches GitHub Pages on for it.

The update address only works from a version that carries it, so an account whose copy is older than 1.3.2 needs 1.3.2 or later put in once. On a Mac with the lock, the lock does that: it installs the newest signed version from the update site, and installing a new copy of the profile makes Firefox do so again in every account at its next start (see the next section). Without the lock, install it by hand once (step 7 above), the last time. Firefox installs an update silently when it asks for no new permissions; a version that adds one waits in each account until someone accepts it (Firefox shows it under the gear menu and in the Add-ons Manager), unless the lock installs it, in which case Firefox grants them itself. The lock's settings also keep **Update Add-ons Automatically** switched on (`ExtensionUpdate`).

**Lock it, so nobody can switch it off (Firefox on a Mac)**

On its own, the add-on can be switched off or removed in the Add-ons Manager by anyone using Firefox. The Firefox lock stops that. Firefox installs the add-on itself and gives no way to switch it off, remove it or take away its access to websites. The lock also turns off private windows (add-ons don't run there unless someone allows it), Firefox's own menu items for Troubleshoot Mode, `about:config` and Refresh Firefox, which could otherwise get round it, and keeps automatic add-on updates switched on. It applies to every account on the Mac, yours included.

On a Mac, Troubleshoot Mode can still be started from outside Firefox, and no add-on runs there. So the lock also gives Firefox its own copy of the built-in list, which Firefox enforces itself: those sites stay blocked in Troubleshoot Mode, and while the add-on is switched off. Firefox takes at most 1,000 entries for it, so the copy holds the whole adult top-level domains `.xxx`, `.porn`, `.sex`, `.adult` and `.sexy` as one entry each (every site on them, listed or not), the test case and the large sites of `starter.txt`, and then the built-in sites people visit most, in that order, until it is full (see **Adding sites**). Firefox blocks them before the add-on gets to them, so for them you see Firefox's **Blocked Page** rather than the add-on's. The other sixty thousand or so built-in sites, and sites added on the settings page, still get the add-on's page, and aren't blocked in Troubleshoot Mode (see **What can still get round it** below).

The lock works alongside another blocker that sets Firefox's settings too, such as Plucky. Both blockers' settings stay in force (**Limits** below has the exceptions).

You need an administrator account, and the Mac has to be online when Firefox first starts in an account, because the lock makes Firefox install the newest signed version from the update site (`https://adviseworn.github.io/family-site-blocker-updates/family-site-blocker.xpi`, see **Let it update itself**). The lock only stops people who don't know an administrator's password: anyone who types one can remove it, even from a Standard account, and then switch the add-on off. A profile installed by hand can't prevent that, because macOS lets an administrator remove it even when it has a removal password of its own. So the person it's for needs a Standard account (**System Settings → Users & Groups**) and mustn't know the password of any administrator account on the Mac.

1. Double-click `mac/family-site-blocker-firefox.mobileconfig`. macOS says the profile was downloaded. That doesn't install it yet.
2. Open **System Settings → General → Device Management**. If **Family Site Blocker for Firefox** is already listed as installed from an earlier copy, select it, click the minus button (**−**) and enter your password, so the new copy replaces it. Then double-click the downloaded **Family Site Blocker for Firefox** and click **Install…**. macOS asks for the name and password of an administrator account. If your own account is one (**Users & Groups** shows "Admin" under your name), that's your login password. Otherwise, someone with an administrator account can type theirs here.
3. Quit Firefox (**Firefox → Quit Firefox**, or ⌘Q; closing its windows isn't enough) and open it again. Firefox only reads the lock when it starts, so until then the add-on can still be switched off. To check that the lock is on, type `about:policies` in the address bar. The **Active** tab lists `Extensions`, with `family-site-blocker@parental-controls.local` under **Locked**, `DisablePrivateBrowsing`, and `WebsiteFilter`, with the built-in sites under **Block**. Settings from other programs are listed there too: Plucky's include `ExtensionSettings`, with its own add-ons. The add-on's settings page says so as well: the lock line of its **Is it working?** board reads "The Firefox lock is in force", and from version 1.8.0 says which copy of the profile is installed, "this version's copy (1.8.0), with 1,000 entries in Firefox's own list" (see **Settings page**). Visiting `exampleadultsite.com` now shows Firefox's **Blocked Page**.
4. Open the Add-ons Manager. Family Site Blocker has no on/off switch any more, and its **⋯** menu says **Can't Be Removed**. If it had been switched off before, Firefox normally switches it back on when the lock installs it. If it's still off (for example because a different version had been installed by hand), it shows a switch to turn it on. Turn it on once, and the switch disappears for good.

Firefox installs the add-on from that address once in each Firefox profile for each copy of the lock, and tries again at the next start if it couldn't fetch it. It doesn't look there again by itself; from version 1.3.2 the add-on updates itself instead (see **Let it update itself**), and the lock lets it. When the lock changes, for example because the built-in list changed (see **Adding sites**), `npm run build` writes a new copy of the profile, and installing it as in steps 1 and 2 gives Firefox the new settings, and makes it install the newest version again in every account at its next start, so an account still on an older copy catches up without anyone at the screen. Each copy says which it is: the profile's description in **Device Management** names the version it was built with ("the copy from version 1.8.0"), and the profile hands the add-on the same stamp through Firefox's `3rdparty` policy (its managed storage, which nothing but a policy can write), so the settings page's lock line says whether the copy installed is the add-on's own version's, an older one ("Install the current profile so Firefox's own list catches up", marked as something to do) or a newer one. A copy from before 1.8.0 carries no stamp, and the line says so. To take the lock off, select the profile in **Device Management**, click the minus button (**−**) and enter an administrator's name and password. Family Site Blocker stays installed and keeps blocking, but it's an ordinary add-on again, so anyone can switch it off.

**Close the Option key, too (optional)**

Holding the Option key (**⌥**) while Firefox opens offers Troubleshoot Mode, where no add-on runs, and Firefox checks that key before it reads the lock. It skips the check when the environment variable `MOZ_DISABLE_SAFE_MODE_KEY` is set, and `mac/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist` is a launch agent that sets it in every account at login, for the apps opened from the Dock, Finder and Spotlight. Neither the add-on nor the profile can put it in place (an add-on can't touch `/Library`, and a profile installed by hand carries settings, not files), so there is an installer package for it on each release's page (**Releases** on GitHub, under **Assets**: `family-site-blocker-firefox-troubleshoot-key-1.5.4.pkg` for 1.5.4), built by **Sign with Mozilla** on GitHub's Mac from `scripts/mac-installer.mjs`:

1. Download the `.pkg` and double-click it. The package isn't signed with Apple (that needs a paid developer account), so macOS says it can't check it for malicious software. Open **System Settings → Privacy & Security**, scroll down, click **Open Anyway** next to its name, and confirm; then double-click it again if it didn't open by itself.
2. Installer shows what it does; click through and give an administrator's name and password, as for the profile. It puts the agent in `/Library/LaunchAgents`, owned by the system, and closes the key at once in every account logged in; the other accounts get it at their next login.

Or by hand, with the file from the unzipped folder, in Terminal (it takes effect in each account at its next login, so log out and in once):

```
sudo cp mac/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist /Library/LaunchAgents/
sudo chown root:wheel /Library/LaunchAgents/local.parental-controls.family-site-blocker.firefox-troubleshoot-key.plist
```

To check, run `launchctl getenv MOZ_DISABLE_SAFE_MODE_KEY` in Terminal: it prints `1`. From then on, holding Option while Firefox opens just opens Firefox. Troubleshoot Mode can still be started from Terminal (`open -a Firefox --args --safe-mode`), which Screen Time (**Content & Privacy → App Restrictions**) can keep out like any other app, and macOS lists the agent under **System Settings → General → Login Items & Extensions**, where an account may be able to switch it off (after which its next login has the key back): it is a hurdle, not a lock. To remove it, delete the file from `/Library/LaunchAgents` with `sudo rm` and log out and in; the package leaves nothing else behind.

**Make the lock hold against the administrator password, too**

Nothing installed on a Mac can hold against someone who types an administrator's password: macOS lets them remove any profile, this lock included, and change anything else. (A Mac that a company enrolls through Apple Business Manager and manages with an MDM service can get a profile that even an administrator can't remove, but that needs an organisation with a D-U-N-S number, an MDM service and erasing the Mac.) So the way to make the lock hold is to make sure nobody, you included, knows the administrator password at a moment's notice. The [locked-away password](#locked-away-password), on a page of its own reached from the settings page, is for that: the password gets a random value that only comes back after a wait of up to 2 days.

Work through the steps in this order. Until step 6 is checked, the new password has a copy you can still get at, so a slip can't lock you out.

1. Turn on FileVault while your everyday account is still an administrator: **System Settings → Privacy & Security → FileVault**. Without it, someone can reset the administrator password from macOS Recovery. Anyone who has its recovery key can do that too, so the key gets locked away with the password in step 5.
   - On macOS 15 Sequoia or earlier, if FileVault is off, turn it on and choose **Create a recovery key and do not use my iCloud account**. The key is shown only once, so write it on paper for now.
   - On macOS 26 Tahoe or later, FileVault may already be on. The Mac keeps the recovery key in the **Passwords** app, which also shows it on your other devices signed in to the same Apple Account, and **Show** next to FileVault shows it again. Click **Show** and write the key on paper for now. Step 7 removes the other copies.
2. Use a Standard account every day, with one separate administrator account. In **System Settings → Users & Groups**, click **Add User…** and make a new **Administrator** account (for example "Mac Admin"). Log out and log in to Mac Admin, which also checks its password works. Don't open Firefox there. In **Users & Groups**, click **ⓘ** next to your everyday account and turn off **Allow this user to administer this computer**. Then click **ⓘ** next to Mac Admin: if it shows **Allow user to reset password using Apple Account** (**Apple ID** on macOS 14 Sonoma), turn that off. A new account usually doesn't show it. Restart, log in to your everyday account and do every step from here on there. When macOS asks for an administrator, type Mac Admin's name and current password. If your everyday account is already Standard and only one other account says "Admin", just check that toggle and carry on.
3. In Firefox, open Family Site Blocker's settings page and, under **Locked-away password**, click **Open the locked-away password page**. There, click **Make one up**. It fills in a random password, such as `k7Qm-x3Fa-PZ9e-wHt2-cR4n`, and selects it. Copy it (**⌘C**).
4. In **Users & Groups**, click **ⓘ** next to Mac Admin, then **Reset…**, and give Mac Admin's current name and password when asked. Paste the new password (**⌘V**) into both boxes and leave the hint empty.
5. Back on the locked-away password page, click in the box, press **⌘A** then **⌘V**, so it holds exactly the password you just set, and press **→** to go to the end. Type a space and the FileVault recovery key, so both come back together. Check that the box shows the whole password, one space, then the key.
6. Try it with a short wait before the long one. Choose **1 minute**, click **Lock it away**, then **Start unlocking**, and check that what appears is the password and the key. Click **Copy**, **Hide** and **Delete it**, then click in the empty box and press **⌘V**. Now choose the real wait (**2 days** is the longest), click **Lock it away**, then **Save a backup file**. When you need the administrator password, click **Start unlocking** and leave the page open for the wait. It stays the same password, so lock it away again the same way afterwards (the page does this by itself).

What can still get round it:

- Troubleshoot Mode started from outside Firefox, for the sites outside Firefox's own copy of the list. On a Mac, holding the Option key (**⌥**) while Firefox opens, or opening it with `--safe-mode`, still offers Troubleshoot Mode, where no add-ons run, this one included; Firefox can stop that only on Windows, and the launch agent above closes the Option key but not the Terminal. Firefox's own copy of the list still blocks there: every site on `.xxx`, `.porn`, `.sex`, `.adult` and `.sexy`, the large sites, and the built-in sites people visit most, 1,000 entries in all. The other built-in sites open, and so do sites added on the settings page, explicit search results and pictures (safe search and the picture filter need the add-on), and images and scripts that an allowed page loads from a blocked site. To keep a site blocked there too, add it to `starter.txt`. Another blocker that works outside the browser covers the rest.
- Browsers other than Firefox, and other editions of Firefox such as Firefox Developer Edition and Firefox Nightly, which the lock doesn't reach. A Standard account can still copy any of them into its own Applications folder. Screen Time (**Content & Privacy**) or another blocker covers those.
- Erasing the Mac and installing macOS again, which deletes everything on it.
- A VPN or proxy app, unless its sites are blocked too (see **Limits**).

### Settings page

To open it later, click the puzzle-piece **Extensions** button in the toolbar and choose **Family Site Blocker** (in Chrome you can pin it there to keep its icon in view). The version installed is shown next to the title: when a new version is going in account by account, that shows which accounts still have the old one. From version 1.7.0 the page is short, and starts with what matters: a board, **Is it working?**, with one line for each thing that has to be right and a mark against it: website access (Firefox can leave it off), private windows, whether anything stops the person at the keyboard switching the add-on off (the Firefox lock in force, or not, and from 1.8.0 which copy of its profile is installed: this version's, an older one that should be replaced, or a newer one; under the lock the private-windows line says the lock turns them off), safe search on at the search engines it covers (see **Safe search** below), pictures and videos being judged (how many since the browser started; see **Pictures**), and the test site, **Open exampleadultsite.com**. In Chrome, Edge and Brave the last line also asks the browser's own rule matcher about six addresses and says whether all six came out right, with the list folded away under **Show the checks**; Firefox doesn't let add-ons run that check, so there the test site is the check. Then come the two settings, **Your blocked sites** and **Pictures** (how strictly pictures are judged), then **The record**: the latest three tries with a link to the whole record, a line on the pictures hidden and one on sites that might belong on the list (see **Blocked attempts**), and last where the **Locked-away password** stands, with a link to its page (see below). Each section links to its part of this README for the detail.

## What it blocks

- The listed domain and every subdomain (`www.`, `m.`, `cdn.`…), on any scheme and port, however the address is written (upper case, trailing dot, `user:pw@`, full-width letters).
- The same site reached indirectly: a link, a popup, a redirect, a form post, a frame inside another page.
- Anything an allowed page tries to load from the site: images, scripts, styles, frames, `fetch`, XHR, WebSockets. These fail silently.
- Lookalikes are left alone: `notexampleadultsite.com`, `exampleadultsite.com.example.org`, `exampleadultsite.co`.

It blocks by domain. It can't block one page of a site, and it doesn't read page content, so an adult site that isn't on the list isn't blocked.

### Safe search

A list can't filter search results, and Google Images, Bing and the rest show explicit results with their own filter off. From version 1.4.0 the extension keeps those filters on: a search on Google, Bing, DuckDuckGo, Yahoo or Brave Search goes out with the engine's strict setting added to its address (`safe=active`, `adlt=strict`, `kp=1`, `vm=r`, `safesearch=strict`), whatever the engine's own settings say and whichever way the search was typed, and every request to YouTube carries the `YouTube-Restrict: Strict` header, which keeps it in Restricted Mode. The browser does this itself from rules the extension gives it (`extension/rules/safe-search.json`, written by `npm run build` from `extension/lib/safesearch.js`), before the request goes out, so there is no moment when the unfiltered page loads; a search whose address already has the setting is left as it is, and so are the engines' other pages. The settings page's **Safe search** section has a Google search to try: the address gains `safe=active`. Other search engines, and sites with a search of their own, aren't covered, and the filters are the engines' own, with their misses. Under the Firefox lock this needs the add-on running, so it doesn't apply in Troubleshoot Mode.

### Pictures

A list of sites can't touch one picture on an ordinary site: a magazine article that opens with a stock photo of a woman in lingerie, say. From version 1.5.0 the extension also judges pictures themselves. Every `<img>` a page shows is kept hidden until the background script has judged it, then shown or kept hidden; icons and other small pictures (under about 64 pixels square) are shown at once, and a long page costs only what comes near the view. The judge is NSFWJS's MobileNetV2 model (MIT) on TensorFlow.js (Apache 2.0), both bundled in `extension/vendor/` and `extension/models/`, run through WebAssembly on this computer: no picture and no score leaves it. It gives five scores that add up to one: drawing, hentai, neutral, porn and sexy, "sexy" being its word for suggestive but not explicit, such as lingerie, swimwear or a pose.

The **Pictures** section of the settings page chooses what is hidden: **Nudity and anything suggestive** (the default: hidden when porn, hentai and sexy together reach 0.4) or **Nudity only** (porn and hentai together reach 0.4). There is no off. The page's **Is it working?** board says how many pictures and video frames were judged and hidden since the browser started, and how the judging runs. Hidden pictures go into the record, and a page of its own, **Pictures hidden** (linked from the record page), lists them by site and one by one: the site, the picture's address, why, and the nudity and suggestive scores. A picture hidden on a score under 0.6 is marked **borderline**, and the summary counts those: that is where a harmless picture hidden by mistake will be. To look at one, **Copy address** and open it in a browser without the extension: in that browser it would be judged and hidden again, and the pictures aren't shown on the page because anyone can open it. Nothing on the page un-hides a picture, for the same reason; if a harmless picture was hidden, the **Nudity only** setting hides fewer. A hidden picture keeps its place on the page, blank; a page's script can't bring one back by taking the mark off, because the picture is judged again at once.

The judge is a machine's, and it errs both ways: it misses some pictures, and hides the odd harmless one (swimwear, art, a medical page), more so under the default setting. Pictures set as CSS backgrounds and pictures inside shadow roots aren't judged, nor is a picture the page made itself (a `blob:` address) or one the background script can't fetch, which are shown as they are. Under the Firefox lock the judging needs the add-on running, so it doesn't happen in Troubleshoot Mode. Judging takes about a tenth of a second a picture through WebAssembly; the first picture after the browser starts waits a moment longer while the model loads.

**Video.** A site that isn't on the list can show a video that a list can't touch either: a TikTok video of a woman in lingerie was the case that showed it (TikTok, like Instagram or X, is deliberately kept off the list). From version 1.6.0 every `<video>` is judged the same way as a picture, and by the same judge. A video stays hidden until its poster, if it has one, and its first frame have been judged; then, while it plays, one frame every second and a half is judged, and one after each seek. A frame is copied small (224 pixels square, as the judge scales it anyway) by the page's content script and judged by the background script like a picture; a video whose frame or poster is judged the way a hidden picture would be is hidden and paused, and stays so for as long as it keeps that source, whatever the page does to its mark; a new source is judged afresh. Hidden videos join the **Pictures hidden** page, marked **video**, under the video's own address, its poster's or, for a video the page made itself (a `blob:` address, as players that stream do), the page's. A hidden video keeps its place on the page, blank, so pages built around one still work; the sound stops with it. What it can't judge: in Chrome, Edge and Brave, a video whose frames the page itself may not read, that is, one served from another site without that site's permission, is judged by its poster alone, or shown as it is when it has none (Firefox lets an add-on read every video's frames, so there it is judged too); videos that stream (YouTube, TikTok, most players) hand the page their frames, so those are judged everywhere. Protected video (films from a subscription service) gives no frames to read and is shown. A video that turns from harmless to not is hidden within a second or two, so a moment of it may be seen. A video inside a shadow root isn't judged, as a picture there isn't.

The **Real pictures check** (`npm run check:pictures`, or the workflow of that name in the Actions tab) judges the real pictures listed in `test/real-pictures.txt` through the extension in Chromium and prints their scores against what the list expects: the lingerie photo from the article above comes out `sexy 0.97`, hidden under the default setting and shown under **Nudity only**; the ordinary photos listed with it come out neutral. When a picture is judged wrongly in use, add a line for it there, so the thresholds in `extension/lib/pictures.js` can be checked against it.

## Adding sites

- **Your blocked sites** on the settings page: one site per line, saved straight away. Pasted addresses are cleaned up (`https://www.Example.com/a?b` becomes `example.com`) and hosts-file lines (`0.0.0.0 example.com`) work too.
- **The built-in list** lives in `blocklists/*.txt`: `starter.txt`, the test case and the large sites, which Firefox's own copy (the lock) takes first; `community.txt`, the "porn" extension of [StevenBlack/hosts](https://github.com/StevenBlack/hosts) on its own, some 64,000 sites gathered from lists its maintainers rebuild every few days (MIT; it holds Clefspeare13/pornhosts and bigdargon/hostsVN's adult list, MIT too); and `popular.txt`, the built-in sites people visit most, in order (below). `npm run blocklist` fetches the latest copies of both; any other `.txt` file saved there is taken too. After a change, run `npm run build`, which rewrites the rules (`extension/rules/`, split into files Mozilla's linter will read) and the lock's profile, then release a new version. Large lists are fine: 400,000 domains in the built-in list and 300,000 pasted into the settings page both worked in testing.
- **Sites to leave out** go in `blocklists/never.txt`, with a reason each. The settings page can't remove built-in sites, and the community list carries the odd ordinary site (a lifestyle magazine, a film database, a search engine), and one entry, `www.b-cdn.net`, that with its `www.` dropped would block Bunny CDN, a network ordinary sites load pictures and scripts from. The build leaves the sites named there out of the rules, `domains.json` and the lock's copy; a line takes out that one domain, so a host listed under it on its own stays blocked. The fast checks make sure those sites and a list of well-known ones never get onto the built-in list (`test/blocker.test.mjs`, `NEVER_LISTED`), and `npm run blocklist` prints the most visited sites on the list whose names don't look adult, as candidates.
- `npm run build` also writes the Firefox lock's profile, `mac/family-site-blocker-firefox.mobileconfig`, with Firefox's own copy of the list, which Firefox enforces itself. Firefox takes at most 1,000 entries there, and they are match patterns, so one entry can take a whole top-level domain: the copy starts with `.xxx`, `.porn`, `.sex`, `.adult` and `.sexy` as one entry each (`scripts/firefox-lock.mjs`, `WHOLE_DOMAINS`; the first four are ICM Registry's adult-only domains, `.sexy` is adult in practice), which cover some 1,300 of the list's sites and every site on those domains that no list has yet, then the sites of `starter.txt`, then `popular.txt` in its order, then the other files by name, until the 1,000 are full. The build says how many sites were left out; the add-on still blocks those while it runs. On a Mac with the lock, install the new profile (steps 1 and 2 of the lock) to bring Firefox's copy up to date; until then the settings page's lock line says an older copy is installed. The build also stamps the profile with the version it was built with and the size of Firefox's copy, and writes the same stamp to `extension/rules/lock.json`, which is how the page tells.
- `popular.txt` is written by `npm run blocklist` from the Chrome UX Report's top million sites, Google's count of real page loads in Chrome, which [zakird/crux-top-lists](https://github.com/zakird/crux-top-lists) caches as a CSV (Google's public dataset, CC BY-SA 4.0 as [Tranco](https://tranco-list.eu/) gives it; the file takes the order of some two thousand sites from a million, not the data). It ranks sites in bands (the top 1,000, 5,000, 10,000, 50,000 and so on) and gives no order within a band, so there the [Majestic Million](https://majestic.com/reports/majestic-million) decides (CC BY 3.0; a ranking by links from across the web, which `npm run blocklist` also fetches), sites it doesn't rank last and alphabetical among themselves. The file lists the built-in sites best band first, with the band and the Majestic place in a comment; every site in it is on `starter.txt` or `community.txt` already. The order matters at the edge: the copy's last band has room for about a third of its sites, and which third used to be the alphabet's choice. Before it, the lock's copy was `starter.txt` and then the community file in file order, which put 938 small Vietnamese sites in Firefox's copy and 18 of the 634 listed sites in the top 10,000 of the web; now the copy holds every one of them (632, two having come off the list in `never.txt`) and 973 of the 1,734 in the top 50,000.

## Blocked attempts

Each time a page on a listed site is opened in a tab, by typing the address, following a link, a redirect or a form post, the extension notes the time and the site. A site is noted under its listed name (`exampleadultsite.com` for `www.exampleadultsite.com/page`), whether the block page stopped it or, on a Mac with the Firefox lock, Firefox's own **Blocked Page** did. Tries at the same site less than two seconds apart count as one, so a reload isn't a new try.

The settings page shows the summary and the latest three under **The record**, newest first. **See the whole record** opens the record page in a tab of its own: the record summed up by site (how many tries, the first and the latest, how many got through), most tried first, the line that says when the browser's history was last looked through (below), with a line each for the two other parts of the record, the pictures hidden and the sites that might belong on the list, which have pages of their own (see below). **See every try** leads to a page of its own with every try, grouped by day, newest first, and choosing a site in the by-site table leads to the same page showing that site alone. **Save as a file**, on both pages, saves the whole record as a CSV file (`family-site-blocker-record-<date>.csv` in the browser's downloads folder), oldest first, with each time in this computer's time zone, for a spreadsheet or for keeping.

If a listed site's page loaded anyway, because the extension had no access to websites yet, say, or its rules were off, the note says **Opened, not blocked** and the summary line counts those pages. That means something on the settings page still needs switching on.

The record starts when the extension starts watching, but the browser's own history goes back further: every page loaded in that browser profile, for months in Firefox and 90 days in Chrome, except in private windows and whatever someone deleted. From version 1.3.4, when the extension is installed or updated it looks through that history for visits to listed sites and adds them, with their original times, marked **Visited (browser history)**; a line on the record page says when it last looked and what it found, and a button there looks again (after adding a site to your list, say). Those entries say the site was visited; whether something else blocked it at the time isn't known. The same visit is never added twice, and a try the extension saw as it happened isn't added again from the history. This is what makes the record an answer to "has this browser been used for such sites", not only from the day the extension arrived.

The browser fills in addresses from its own history and bookmarks, blocked sites included: a blocked try still puts the typed address into the history, where typing its first letter brings it back. So once a try is in the record, the extension takes the site's pages out of the browser's history, and removes bookmarks to listed sites: the earlier visits the history scan found (the record page's line says how many pages and bookmarks went), and each new try a moment after it is noted. The record keeps them all, with their times, so the record page is the place to look, not the browser's own history window. Sites pinned by hand on Firefox's new-tab page, and what Firefox suggests from the web rather than from this profile, aren't touched.

No list is complete: new sites appear every week, and the community list lags behind on the newest kind. So the same look through the history also notes sites that aren't on either list but look adult from their names (`porn`, `hentai`, `nsfw`, `escort`, a `.xxx` address, and so on, judged with care so that `essex.gov.uk` and `peacocktv.com` are left alone). The settings page says how many there are, and a page of its own, **Not on the list, but might belong there** (linked from the settings page and the record page), lists them, most visited first, with the number of visits and the last one. They are not blocked; **Add to your list** puts one on your list (the same list as the box on the settings page, which updates), blocks it from then on in that browser, and has the history looked through again, so its earlier visits join the record and it leaves the table. Only the name is judged: a plain name such as `swappz.com` passes unnoticed, which is why those still need adding by hand when you meet one.

Nothing on either page clears the record, and the pages have no PIN, so anyone who opens them can read it. The record stays until the extension is removed (which the Firefox lock prevents) or the browser profile is deleted, and only the oldest notes go once there are more than 10,000 (1,000 before version 1.3.5). Like the sites you add, it is kept in the browser's own storage for the extension, so Firefox drops it when it quits if the add-on isn't signed, and it never leaves the computer: the add-on still collects no data in Mozilla's sense.

What it doesn't see:

- Images, scripts and frames that another page loads from a listed site. Those are blocked silently, and they aren't the person's doing.
- Anything in another browser, or in Firefox's Troubleshoot Mode, where the add-on doesn't run. Firefox's own copy of the list still blocks the built-in sites there, but nothing is noted.
- Private windows, unless the extension is allowed there (the settings page says whether it is). Under the Firefox lock there are none.
- Tries while the extension was off, or sites that aren't on either list, unless the browser's history has them (see above).

To note attempts, the extension asks the browser to tell it about page loads (the `webNavigation` and `webRequest` permissions), to read and change its history (`history`), and to remove bookmarks (`bookmarks`). Firefox's add-on permission prompt calls those "Access browser activity during navigation", "Access browsing history" and "Read and modify bookmarks".

## Locked-away password

The extension can keep a password that you only get back after a wait you choose, from 1 minute to 2 days. It's meant for putting something out of your own quick reach, such as this computer's administrator password, in the same way as [Lockbox Local](https://github.com/bleriotnoguia/lockbox-local). It has a page of its own: the settings page's **Locked-away password** section says where it stands (none, locked away, or how far unlocking has got) and **Open the locked-away password page** opens it.

1. On that page, type the password, choose the wait and click **Lock it away**.
2. Click **Save a backup file**. Removing the extension deletes the password with it, and so does Firefox when it quits if the add-on isn't signed. The backup file stays locked with the same wait, so it's safe to keep anywhere.
3. To get the password back, click **Start unlocking** and leave the page open. When the wait is over the password appears, and it's locked away again straight away with the same wait.

The wait is computing time, not a timer. The password is encrypted with a key that can only be worked out by squaring a 2048-bit number over and over, each step needing the one before (a time-lock puzzle), and the number of steps is set by timing this computer. Reading the extension's storage or the backup file, or changing the computer's clock, doesn't skip it. While it runs, one processor core is busy. If the page is closed or the computer sleeps, the work pauses, and it carries on from where it got to when you open the page and click **Carry on unlocking**. **Stop unlocking** throws the work away.

What it can't do:

- Someone who writes a faster program for the same puzzle can shorten the wait, perhaps several times over, though not skip it.
- It doesn't stop anyone resetting the administrator password another way, such as from macOS Recovery, unless FileVault is on and its recovery key is locked away too (see **Make the lock hold against the administrator password, too**).
- A faster or slower computer than the one that locked it takes less or more time.

## Tests

```
npm test                  # fast checks (the picture classifier's own test needs npm install)
npm install               # once, for the Chromium tests
npx playwright install chromium    # once, if Playwright has no browser yet
npm run test:browser      # 75 tests in a real Chromium
npm run test:firefox      # 42 tests in the Firefox installed on this computer
```

`npm run test:browser` loads the extension the way "Load unpacked" does and drives it like a person would. `npm run test:firefox` does the same in Firefox. It builds the zip that `npm run package:firefox` makes, loads it the way "Load Temporary Add-on…" does, and then checks that the `extension` folder itself loads too. It finds Firefox in its usual place on macOS, Windows or Linux, or uses the one in `FIREFOX`, and is skipped if there is none. Its last group gives a Firefox with no add-on the lock's own copy of the list, through Firefox's own `policies.json` (next to the program on Linux and Windows; inside the app on a Mac, which needs an administrator, so there it runs only on GitHub), and checks that Firefox takes all 1,000 entries and blocks the whole adult domains (`tik.porn`, a `.porn` site no list has) and the sites that fill the copy, while ordinary sites and `never.txt`'s load.

On GitHub, every push runs all three suites on a GitHub-hosted Mac (`.github/workflows/macos.yml`) and on a Linux machine (`.github/workflows/linux.yml`, with Mozilla's own Firefox build), since GitHub's Macs are often scarce. The Mac also builds the installer package that closes Firefox's Option key, installs it with sudo, checks the agent it left (owner, mode, loaded for the account, `launchctl getenv`) and takes it away again (`npm run test:mac-installer`; like the lock tests, it only runs on a Mac in CI, because installing changes every account). Each run lists the system, Chromium and Firefox versions and each suite's totals, and fails if any test was skipped, except the one check that needs a Mac.

The Firefox lock has its own tests, which need a signed `.xpi`: `SIGNED_XPI=path/to/signed.xpi npm run test:firefox-lock`. They put the lock in force (installing from the test's stand-in internet instead of the update site), check that Firefox installs the add-on and won't let it be switched off, check that a new copy of the lock naming a different address makes Firefox install the newer version in an existing profile with its permissions, check that Troubleshoot Mode (started with `--safe-mode`, as the Option key does) still blocks the sites in Firefox's own copy of the list and every site on the whole adult domains, and take the lock away again. With a signed version 1.3.0 or later, they also check that a try Firefox's own copy of the list stopped is noted under **Blocked attempts**, not marked as opened; with 1.7.0 or later, that the settings page's lock line says the lock is in force, and with 1.8.0 or later which copy of the profile is installed, from the stamp (the lock under test is built from the checkout, the add-on is the signed one, so the line says this version's copy, an older one or a newer one as the two versions compare), and that private windows are said to be off. They check too that Firefox hands the add-on the stamp as its managed storage. With `OLDER_XPI` set as well, they check that the add-on updates itself: with the lock installing the older version, Firefox reads an update manifest made from the newer signed version (served by the test's stand-in internet), refuses a file whose hash doesn't match, installs the right one, and stays locked. A control in that group starts Troubleshoot Mode with the lock as it was before it carried the list, where `exampleadultsite.com` loads. With `OTHER_XPI` set to another program's signed add-on (GitHub uses LeechBlock NG, a site blocker), they also put the lock next to another blocker's settings, made like Plucky's, and check that both blockers stay installed and locked. With `OLDER_XPI` set to an earlier signed version of this add-on, they check what happens when that version was installed by hand and switched off before the lock, and that a newer version still installs over a locked one. On a Mac they only run on GitHub (**Firefox lock check** in the Actions tab), because the lock covers every account on the computer.

No real website is contacted: every request goes to a small local server instead, so a request that never reaches that server was stopped by the browser. The picture filter is tested with a copy of the extension whose classifier judges a picture by its address instead of its pixels, and a video's frame by its colour (`test/helpers/pictures.mjs`; the videos in `test/fixtures/` are two seconds of one colour each, and one that turns from blue to red), so no explicit picture is needed, and with the real classifier on two ordinary photos (`test/fixtures/`, from TensorFlow.js's examples, Apache 2.0); `npm test` also runs the real model in Node on those photos. In both suites the first group is the test case itself, with a control that shows the site loading when the extension isn't installed. Set `HEADFUL=1` to watch the browser, or `EXTENSION_DIR=/path/to/build` to test a different build.

## Limits

- It is a browser extension. Safari, other browser profiles and apps are not covered. In Firefox it stays installed only until Firefox quits, unless Mozilla signs it.
- It updates itself only in Firefox, from version 1.3.2, and only while the update files are published (see **Let it update itself**). In Chrome, Edge and Brave, an extension loaded unpacked is updated by replacing the folder's files and reloading it on the extensions page.
- Without a lock, anyone who can open the extensions page can turn it off or remove it, and the settings page has no PIN (its **Is it working?** board says whether the lock is in force). Firefox on a Mac has the lock above, which anyone who knows an administrator's password can take off. In Chrome and Edge, an administrator can force-install the extension with the `ExtensionInstallForcelist` policy and turn off Incognito with `IncognitoModeAvailability`, which needs the extension packaged and published. The lock only covers Firefox, so on a child's account, keep other browsers out with account or system controls.
- Sites added on the settings page are kept in the Firefox profile, so deleting the profile folder loses them (the add-on comes back by itself under the lock). For sites that must stay blocked whatever happens, add them to the built-in list. The record of blocked attempts is kept there too, and goes with it.
- The lock installs the add-on once in each Firefox profile. If someone deletes the add-on's file from inside their Firefox profile folder while Firefox is closed, Firefox doesn't put it back: it's missing from the Add-ons Manager until you install it again from the folder.
- Firefox takes each of its settings from one place. The lock leaves out the one other blockers use for their own add-ons (`ExtensionSettings`), so theirs keep working, and its other settings are the same as Plucky's, apart from `WebsiteFilter` (Firefox's own copy of the built-in list). If another program sets `Preferences` differently, Firefox uses the lock's (which keeps add-ons' blocking switched on) instead of that program's. If another program also sets `WebsiteFilter`, Firefox uses the lock's list and drops that program's. The same goes for `3rdparty`, which carries the lock's stamp: a program that uses it to configure its own add-ons would lose those settings (Plucky doesn't use it). To check before installing the lock on a Mac with another blocker, look for `WebsiteFilter` and `3rdparty` on `about:policies`.
- Firefox's own copy of the built-in list takes at most 1,000 entries (five whole adult domains, the large sites and the sites people visit most; see **Adding sites**), stops pages and frames but not images, scripts or other things an allowed page loads, and shows Firefox's **Blocked Page** rather than the add-on's. While the add-on runs, it covers the rest.
- Reaching a site by its IP address, through a proxy or VPN, or through a translation or cache service is not covered unless that address is on the list too.
- The picture filter judges `<img>` pictures and `<video>` frames, by a machine that errs both ways; see **Pictures** for what it leaves out (backgrounds, protected video, frames the page may not read).
- Safe search covers five search engines and YouTube, with the filters those sites provide. Reddit, X, Discord, Telegram and other platforms carry adult content under their own domains, which a list can't separate from the rest.

It fetches version 1.1.1 from Mozilla with the API key that **Sign with Mozilla** uses. Started by hand from the Actions tab. |
| `.github/workflows/macos.yml`, `.github/workflows/linux.yml` | Run all the tests on a Mac and on a Linux machine at GitHub after every push. |
| `test/real-pictures.check.mjs`, `test/real-pictures.txt`, `.github/workflows/pictures-check.yml` | **Real pictures check** (`npm run check:pictures`): judges the real pictures listed through the extension in Chromium and prints their scores against what the list expects. Contacts real websites, so it isn't part of `npm test`. Started by hand from the Actions tab. |
| `.github/workflows/firefox-package.yml` | Builds the Firefox zip and checks it with Mozilla's add-on linter after every push. |
| `.github/workflows/sign-firefox.yml` | **Sign with Mozilla**: gets the add-on signed and publishes the signed files as a release, then runs **Publish updates**. Started by hand from the Actions tab. |
| `.github/workflows/publish-updates.yml` | **Publish updates**: builds `updates.json` and the signed `.xpi` files from every release with `scripts/updates-manifest.mjs` and pushes them to the public updates repository, whose GitHub Pages site Firefox reads. Runs after **Sign with Mozilla**, or by hand from the Actions tab. |
| `scripts/updates-manifest.mjs` | Makes the update manifest Firefox reads, with each signed version's address and hash, and the rest of the updates site. |
| `scripts/check-signed.mjs` | Checks that a signed `.xpi` holds exactly the files that were uploaded, plus Mozilla's signature. |
| `scripts/amo-signed.mjs` | Downloads a version Mozilla has already signed, for **Sign with Mozilla**. Tested against a stand-in for Mozilla's API (`test/amo.test.mjs`). |
